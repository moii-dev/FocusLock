# FocusLock — StayActive

Расширение Google Chrome на Manifest V3. Название расширения в Chrome — **FocusLock**, название интерфейса popup — **StayActive**.

Для выбранного домена расширение скрывает стандартные сигналы потери видимости и фокуса страницы. Все домены изначально выключены. Файлы готовы для **Load unpacked**: сборка, npm install и внешние библиотеки для расширения не нужны.

## Установка

1. Откройте `chrome://extensions`.
2. Включите **Developer mode / Режим разработчика**.
3. Нажмите **Load unpacked / Загрузить распакованное расширение**.
4. Выберите папку **FocusLock**, в которой находится `manifest.json`.
5. Откройте обычный HTTP/HTTPS-сайт, нажмите значок расширения и включите **Stay active on this site**.
6. Разрешите Chrome доступ к этому домену. Нажмите **Reload tab**, чтобы перехваты установились с начала загрузки.

Требуется Chrome 119 или новее. На `chrome://`, страницах других расширений, Chrome Web Store, `file://` и IPv6 URL расширение не включается. Локальный стенд открывайте через HTTP, а не двойным щелчком по HTML.

### Обновление с 1.0.0 до 1.1.0

В `chrome://extensions` нажмите кнопку обновления на карточке FocusLock. Затем **перезагрузите вкладку сайта** и откройте popup снова. Обновление расширения не заменяет уже исполненный MAIN-код в существующем документе. Без перезагрузки вкладки там может остаться версия 1.0.0.

Popup 1.1.0 проверяет наличие контроллера текущей версии, фактические getters и совпадение настроек. Сохранённый переключатель сам по себе больше не выдаётся за установленную защиту. Для позднего внедрения показывается предупреждение о перезагрузке.

При разборе публичного HTML [указанной страницы](https://smmnakrutka.ru/free-telegram-followers) обнаружен секундный таймер, который запускается на `load`/`focus` окна и отменяется на `blur`. В 1.1.0 добавлен отдельный фильтр зарегистрированных обработчиков этих событий и расширен локальный стенд для такого механизма. Это анализ исходного кода; работа расширения на сайте в браузере не проверялась, услуги сайта не запрашивались, его backend не изменялся.

## Архитектура и раннее внедрение

Архитектура выбрана до реализации с учётом двух ограничений: `MAIN`-скрипт не имеет привилегированного доступа к storage, а асинхронный запрос настроек после `document_start` даёт сайту время зарегистрировать обработчики.

Поэтому используется динамическая **постоянная регистрация** через `chrome.scripting.registerContentScripts`:

```text
Popup → запрос разрешения на конкретный хост → service worker
  → chrome.storage.local: site:<hostname>
  → register/updateContentScripts
      world: MAIN
      runAt: document_start
      persistAcrossSessions: true
      js: [статический bootstrap настроек, scripts/main.js]
```

Четыре опции дают 16 комбинаций. Все 16 маленьких bootstrap-файлов заранее включены в расширение. Service worker выбирает нужный файл при регистрации. Настройки доступны в MAIN синхронно, без запроса к worker, DOM-моста, внешних скриптов и `eval`.

Chrome исполняет файлы из массива `js` последовательно. Сам `scripts/main.js` устанавливает getters и capture-обработчики непосредственно при исполнении. Постоянная регистрация сохраняется между сессиями и не зависит от того, бодрствует ли service worker при навигации. При запуске worker регистрация сверяется с настройками и разрешениями; существующие записи обновляются без промежуточного снятия защиты. При отключении домена регистрация удаляется.

Настройки для уже открытых вкладок этого хоста применяются через `executeScript` сразу, в том числе к доступным соответствующим фреймам. Перед внедрением проверяются хосты фреймов, чтобы не менять настройки другого разрешённого домена внутри смешанной страницы. Такая поздняя установка не может отменить уже вызванные обработчики или забыть сохранённые сайтом оригинальные API. Для ранней установки нужна перезагрузка. `injectImmediately` сам по себе не гарантирует `document_start`.

`allFrames: true` защищает каждый фрейм, который соответствует разрешённому хосту. `matchOriginAsFallback: true` охватывает наследующие этот origin `about:blank`, `blob:` и подобные фреймы. Чужие origin не получают защиту автоматически. Настройки открытого фрейма внутри вкладки с другим верхним доменом гарантированно обновятся при следующей навигации этого фрейма или перезагрузке вкладки.

## Permissions

Обязательные разрешения:

| Permission | Назначение |
| --- | --- |
| `activeTab` | Получить URL активной вкладки после открытия popup, без постоянного `tabs` |
| `scripting` | Регистрировать ранний MAIN-скрипт и применить изменения к открытым страницам |
| `storage` | Хранить настройки локально, отдельно для каждого hostname |

`optional_host_permissions` объявляет `http://*/*` и `https://*/*` как допустимый диапазон **будущих** запросов. Это не выдаёт доступ ко всем сайтам при установке. Popup запрашивает только `http://example.com/*` и `https://example.com/*` для выбранного хоста, непосредственно из пользовательского действия. `<all_urls>`, обязательных host permissions, `tabs`, `webNavigation`, `debugger`, `offscreen`, `alarms` и `webRequest` нет.

Одного `activeTab` недостаточно для автоматического раннего внедрения после будущих навигаций и перезапуска Chrome: это временный доступ, выданный пользовательским действием. Поэтому для включённых доменов нужен постоянный optional host grant.

При выключении защитные настройки отключаются, динамическая регистрация удаляется, но ранее выданный доступ к этому хосту сохраняется: это позволяет восстановить оригинальные свойства во всех уже открытых доступных вкладках и включить домен снова. Отозвать grant можно в Chrome → Extensions → FocusLock → Details → Site access. При отзыве разрешения расширение выключает соответствующую сохранённую настройку и снимает регистрацию. Уже внедрённый код невозможно надёжно удалить из страницы после утраты доступа; перезагрузите такие вкладки. Аналогично перезагрузите страницы после отключения/удаления самого расширения.

## Настройки

Настройки хранятся в `chrome.storage.local` под ключом `site:<hostname>`. Содержимое страницы не получает доступа к хранилищу; доступ ограничен `TRUSTED_CONTEXTS`.

Одинаковый hostname в HTTP/HTTPS и на разных портах использует одну настройку. `example.com`, `www.example.com`, `localhost` и `127.0.0.1` — разные записи. Пути URL, scheme и содержимое страниц не сохраняются. Параллельные изменения worker обрабатывает последовательно.

| Опция | По умолчанию | Поведение при включённом домене |
| --- | --- | --- |
| Stay active on this site | Выключена | Главный переключатель всех перехватов |
| Hide tab visibility | Включена | `document.hidden=false`, `visibilityState='visible'`, совместимые webkit getters; скрывает доверенные document/window visibilitychange |
| Prevent blur detection | Включена | `document.hasFocus()=true`; скрывает доверенные focus/blur документа и окна |
| Keep timers accurate | Выключена | Ограниченное восстановление функциональных interval callbacks при следующем пробуждении JS |
| Developer diagnostics | Выключена | Логи регистрации обработчиков, поступающих/подавленных событий и interval recovery |

Опции можно настроить до включения домена. Пока главный переключатель выключен, они не защищают страницу.

## Аккуратное обращение с событиями

Перехваты стоят в capture-фазе на `window`, максимально рано. Для стандартных document/window сигналов, которые должны оставаться неизменными с точки зрения сайта, вызывается `stopImmediatePropagation()`. Скрываются и переход в фон, и обратное событие: виртуальная страница всё время остаётся видимой и сфокусированной, поэтому обратный сигнал также раскрыл бы переход.

Обычные переходы между элементами через `focus`/`blur` и `focusin`/`focusout` остаются рабочими. Дополнительно скрываются сигналы ухода со страницы, направленные на всё ещё активный элемент: проверяются оригинальный `hasFocus()`, `activeElement` и `relatedTarget`. Соответствующая пара возвращения в тот же элемент также фильтруется. Синтетические события, отправленные самим сайтом через `dispatchEvent`, пропускаются.

Обработчики root-сигналов, зарегистрированные через `addEventListener` на `window`/`document`, получают дополнительный callback-фильтр. Он работает независимо от диагностической опции и при выключении настроек пропускает события. Сохраняются `this`, объектные `handleEvent` listeners, capture, passive, once, AbortSignal и удаление по исходному callback. Подавленное событие не расходует once-обработчик. Обработчики других событий и прямые обработчики элементов не оборачиваются. Capture-перехват также охватывает обычные `onblur`, `onfocus`, `onvisibilitychange` handlers.

Getters и `hasFocus` устанавливаются на прототипе и самом документе. Защищённый getter, заимствованный из другого защищённого same-host контекста, применяет подмену также к документу этого хоста, а не только к документу исходного realm.

`pagehide`, `pageshow`, `freeze`, `resume`, `beforeunload` только наблюдаются. Они не блокируются и не подделываются: это реальные переходы навигации, BFCache и состояния исполнения. Их глобальное подавление мешало бы сохранению состояния и восстановлению страницы, а блокировка `freeze` не остановила бы заморозку renderer. Из этих событий сайт всё ещё может получить информацию о жизненном цикле. Навигация и заморозка не выдаются за обычное переключение вкладки.

При выключении опций оригинальные дескрипторы видимости/hasFocus восстанавливаются, если сайт или другое расширение не заменили их после FocusLock. Неактивные capture-наблюдатели и root callback-фильтры остаются в текущем документе до перезагрузки и пропускают события. Уже созданные managed intervals сохраняют настоящие числовые Chrome ID; clear wrappers остаются до их очистки, чтобы корректно обслужить эти ID.

Это совместимая подмена распространённых API, а не гарантия невидимости расширения. MAIN разделяет среду с сайтом: сайт может обнаружить/изменить подмену, использовать оригинальный getter из другого realm, собственные iframe, данные сервера, задержки JS, состояние media или другие сигналы. Расширение не скрывает все возможные способы определения фонового исполнения.

## Таймеры и реальные ограничения MV3

Chrome принимает решения о фоновой частоте таймеров по внутреннему состоянию вкладки, а не по подменённому JS-getter `document.hidden`. `requestAnimationFrame` в фоне также может приостанавливаться. При freeze, discard, сне системы и закрытии вкладки никакие hooks не обеспечат непрерывное выполнение её JS.

Публичного MV3 API для «отключения throttling» вкладки нет. Service worker не является постоянно работающей фоновой страницей. `chrome.alarms` не предназначен для секундного таймера; dedicated Web Worker и offscreen document тоже не обеспечивают безусловное исполнение callbacks сайта. Расширение не создаёт фиктивный API, не играет бесшумный звук, не имитирует WebRTC и не запрашивает debugger для обхода планировщика.

**Keep timers accurate** — явно включаемая совместимостная мера:

- Оборачивает новые функциональные `setInterval` с периодом от 250 мс до максимального положительного 32-битного timeout.
- Сравнивает ожидаемый запуск с `performance.now()` и при реальном запуске Chrome выполняет до **10** пропущенных callbacks суммарно, включая текущий вызов.
- Сохраняет аргументы callback, `this=window`, настоящий timer ID и отмену через `clearInterval` или `clearTimeout`, в том числе отмену из собственного callback.
- Остальные пропуски учитываются в `skippedTicks`, но не воспроизводятся: иначе длительная заморозка могла бы вызвать тысячи операций сразу.
- Быстрые loops, строковые callbacks и `setTimeout` исполняются Chrome как обычно. Callback, бросивший исключение, прерывает текущий пакет восстановления и сообщает ошибку страницы.

Этот режим может улучшить короткий секундный счётчик вида `seconds++`. Он **не** гарантирует точность такого счётчика при длительном throttling и может запускать несколько побочных эффектов подряд. Для сайтов с сетевыми запросами, платежными операциями или игровой логикой предпочтительнее оставить его выключенным. Для существующих intervals нужна перезагрузка; задним числом их callbacks перехватить нельзя.

Рекурсивная цепочка `setTimeout` не сообщает расширению, сколько логических шагов сайт считает одной секундой. Произвольную логику такого таймера безопасно восстановить невозможно.

**Наиболее надёжный вариант, если можно изменить сайт**, — вычислять время по deadline или времени начала. Таймер только обновляет отображение:

```js
const deadline = Date.now() + 10 * 60 * 1000;
let completed = false;
setInterval(() => {
  const remainingMs = Math.max(0, deadline - Date.now());
  renderRemaining(remainingMs);
  if (!remainingMs && !completed) {
    completed = true;
    onComplete();
  }
}, 1000);
```

Можно использовать такую же формулу внутри рекурсивного `setTimeout`: количество callbacks больше не определяет время. UI и `onComplete` выполнятся при следующем разрешённом запуске JS, а значение времени будет корректным. Для сохранения через reload сохраняйте deadline в storage сайта. `Date.now()` учитывает реальное прошедшее время, включая сон, но зависит от изменения системных часов; для критичных сроков используйте серверный deadline и проверку сервером. `performance.now()` подходит для монотонных интервалов в текущем документе, однако поведение во время сна системы зависит от платформы. Готовый пример для сайта — `test/deadline-clock.js`.

## Диагностический режим

Включите **Developer diagnostics**, перезагрузите страницу и откройте её DevTools → Console. Разрешите уровень **Verbose**, фильтр — `StayActive`.

Логи показывают:

- `listener registered`: попытки зарегистрировать отслеживаемые `addEventListener` после установки диагностики;
- `suppressed event`: доверенные сигналы окна/документа, которые не получил сайт;
- `observed event`: пропущенные lifecycle, synthetic и element events;
- `interval recovery`: сколько callbacks ожидалось, воспроизведено и пропущено;
- `configuration` и доступные ошибки установки дескриптора.

Для каждого вида лога первые 30 сообщений выводятся полностью, далее каждое сотое. Счётчики продолжают обновляться. Callback-функции, текст страницы и введённые данные не логируются. Ничего не отправляется по сети.

Снимок состояния доступен в консоли MAIN страницы:

```js
window[Symbol.for('focuslock.controller.v1')]?.snapshot()
```

Возвращает версию и источник установки (`document_start` или `live`), настройки, фактические document getters, observed/suppressed/registration counters, recovered/skipped ticks и количество managed intervals. Назначения `on*` свойств отдельно не инструментируются; поступление таких событий видно по журналу. Историю слушателей, зарегистрированных до позднего включения, получить нельзя — перезагрузите страницу. Диагностика работает только при включённом главном переключателе.

## Локальная тестовая страница

Страница отображает `document.hidden`, `document.visibilityState`, `document.hasFocus()`, количество window blur/focus и visibilitychange, секундный callback-счётчик, время по дате начала и расхождение. Дополнительно есть проверка фокуса полей, synthetic blur, early head probe, журнал lifecycle и снимок диагностики. В версии 1.1.0 добавлены document focusin/focusout и отдельный пятиминутный таймер, отменяемый через window.blur и запускаемый через load/focus. Его собственный счётчик остановок позволяет отличить отмену таймера сайтом от задержки исполнения Chrome.

Для запуска понадобится Node.js, только для локального сервера:

```powershell
cd C:\Users\moiiu\Desktop\Project\FocusLock
node tools/serve.mjs
```

Откройте [локальную тестовую страницу](http://127.0.0.1:8765/). Остановить сервер можно `Ctrl+C`. Другой порт: `node tools/serve.mjs 9000`. Сервер слушает только `127.0.0.1` и отдаёт только файлы `test/`.

Проверка вручную:

1. При выключенном расширении переключитесь во вторую вкладку/другое окно, вернитесь и посмотрите исходные счётчики.
2. Включите домен и diagnostics. Нажмите **Reload tab**. В первом скрипте страницы должно быть `hidden:false`, `visibilityState:"visible"`, `hasFocus:true`.
3. Сбросьте счётчики, переключайтесь между вкладками, окнами и сверните Chrome. Вернитесь: документ должен показывать false/visible/true, а счётчики стандартных скрытых сигналов не должны расти от этих действий. Диагностика должна показывать suppressed events. У отдельного таймера с window.blur не должно появляться остановок от переключения вкладок. Повторите с фокусом в поле: уход в другую вкладку не должен выглядеть как обычный blur этого поля, а переход A → B внутри страницы должен остаться рабочим.
4. Перейдите между полями A/B: element focus/blur должны увеличиваться. Нажмите synthetic blur: window blur должен увеличиться на один.
5. Отключайте Hide tab visibility и Prevent blur detection по отдельности: соответствующие getters и события должны вернуться к обычному поведению. Полностью выключите домен и повторите проверку.
6. Включите Keep timers accurate и перезагрузите. Оставьте страницу в фоне на несколько минут, затем сравните interval ticks и elapsed time. На обычной странице гарантией является именно elapsed time; skipped ticks при сильном throttling допустимы и задокументированы.
7. Откройте [тот же стенд через localhost](http://localhost:8765/): настройка для `127.0.0.1` не должна включить `localhost`. IPv4-адрес localhost должен разрешаться на 127.0.0.1.
8. Перезапустите Chrome: включённый домен и постоянная ранняя регистрация должны сохраниться. Проверьте навигацию назад/вперёд: lifecycle events должны продолжить работать.
9. Проверьте DevTools страницы, popup и service worker на ошибки. Console errors от сайта отличаются от `[StayActive]` diagnostic debug logs.

**Статус проверки:** по последнему указанию пользователя расширение и стенд не запускались для самостоятельного тестирования. Это инструкция для вашей проверки; прохождение аудита/браузерных тестов не заявляется.

## Официальные источники

Технические решения опираются на документацию Chrome:

- [Scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting) — MAIN, порядок файлов, document_start, постоянные динамические регистрации и ограничения executeScript.
- [Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) — execution worlds и момент внедрения.
- [Permissions API](https://developer.chrome.com/docs/extensions/reference/api/permissions) — optional grants и запрос из пользовательского действия.
- [activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) — временный доступ к активной вкладке.
- [Background timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88/) — ограничения фонового исполнения.
- [Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) — freeze, discard, pagehide/pageshow и восстановление.
- [Service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) — ограниченная продолжительность жизни worker.
- [Alarms API](https://developer.chrome.com/docs/extensions/reference/api/alarms) — alarms не являются заменой секундных JS-таймеров страницы.
